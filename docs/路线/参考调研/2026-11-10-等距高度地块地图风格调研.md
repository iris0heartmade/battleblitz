## 1. TL;DR — 一句话结论

**有成熟开源方案，不需要自研渲染器；但 BattleBlitz 这次不是"换个皮"，而是整套地图数据模型 + 渲染管线 + 美术资产的换血。**

- **引擎层面**：Godot 4 的 `TileMapLayer` **原生支持等距网格**（Tile Shape = Isometric / Diamond Down），配合「高度分层 + z_index + y_sort」是社区验证过的成熟做法，有可直接抄的开源 demo。
- **开源项目**：至少 4 个可参考的 Godot 等距项目 + 3 套可商用的等距资产包（见 §8）。
- **最大风险不在技术，在美术**：等距立方体地块的「顶面 + 两个侧面」贴图，比现有 48×48 正视角贴图多出 3 倍工作量。
- **给老大的建议**：先做**路线 A（2D 等距 + 分层高度）**，因为它保留现有 2D 精灵管线、保留现有 UI、保留现有 Python 后端，改动集中在地图渲染层；路线 B（真 3D）效果最好但要把整个客户端从 2D 迁到 3D，属于另一个项目量级。

## 2. 需求精确化：三个特征各自主张什么

老大描述的目标风格有三个独立特征，它们在技术上**不是同一件事**，拆开看才不会混：

| # | 特征 | 技术含义 | 实现难度 | 与"山脉难画"的关系 |
|---|------|---------|:---:|---|
| ① | **45° 倾斜俯视** | 等距投影（Isometric），格子在屏幕上呈菱形 | ⭐ 低 | 无关。这是"看起来立体"的前提 |
| ② | **方形地块** | 逻辑网格是 square grid，不是 hex | ⭐ 低 | 无关。但决定了不能沿用六边形战棋那套邻接规则 |
| ③ | **地块高度差** | 每格有 elevation 整数，视觉上是立方体，不同高度有可见侧面 | ⭐⭐⭐ 高 | **这才是解决山脉痛点的核心** |

**关键洞察（这是本次调研最有价值的一条）**：

> 山脉难画，**根源不是视角问题，而是"平面贴图无法表达垂直落差"**。
>
> 纯 2D 俯视图里，一座山和一片草地都是平铺的格子，画家只能靠"画一坨山的图案"来暗示立体，结果就是：山脉边缘生硬、看不出高低、与相邻地块的关系模糊。
>
> 引入真实 elevation 后，山脉 = **一叠高低不同的立方体**，侧面自然形成落差台阶，画家只需画好"顶面纹理 + 侧面岩石纹理"两套素材，山脉的立体感**由几何自动生成**，不再靠手绘技巧硬凑。
>
> 也就是说：①和②是"重新包装"，③才是"真正解决问题"。如果只做①不做③，等距只是换了个角度的山脉难画问题。

## 3. 先纠正一个史实（关系到美术量级）

老大记忆里的「GBA 最终幻想战略版也是这种风格」——**需要拆成两半看**：

| 作品 | 平台 | 45° 等距方格 | 地块高度差 |
|------|------|:---:|:---:|
| **Tactics Ogre（皇家骑士团）** | SFC / GBA | ✅ | ✅ **有高低地形** |
| **Final Fantasy Tactics** | PS1 | ✅ | ✅ **有 elevation + Jump 跳跃属性** |
| **Final Fantasy Tactics Advance** | **GBA** | ✅ | ❌ **没有高度差，全是平地** |

核实依据：
- FFT（PS1）的地图设计被公认为 SRPG 教科书，ResetEra 上有专门的"FFT 地图设计为什么重要"长帖，总结出第一原则就是「Vertical gameplay — 地形高低对战术影响极大」，并明确提到单位有 **Jump 属性**决定能跨越多高的落差。
- FFTA（GBA）的评测普遍指出它是"简化版"，相对前作**砍掉了高度差等复杂因素**，地形只需考虑水。
- 反倒是 SFC/GBA 的《皇家骑士团》被中文媒体评价为「利用创新的 45 度视角画面，在不具备 3D 多边形的硬件条件下，实现了各种自然环境和高低地形效果」。

**这个纠正的实际意义**：

> GBA 能跑出高低地形，靠的不是"引擎支持"，而是**纯手工预渲染的立方体贴图 + 精确到像素的遮挡排序**。GBA 只有 4 个 BG 图层和 128 个精灵，硬件完全不支持 per-cell elevation，是 Square/Quest 的美术和程序一起手抠出来的。
>
> 对我们的含义：**这条路是可行的，但 Godot 不会替你做这件事**——Godot 4 的 2D TileMap **没有原生的"每格高度"字段**，高度要么靠分层模拟，要么自己写渲染器。这一点是本次调研最重要的技术结论（详见 §5.3）。

## 4. 三条技术路线对比

```
BattleBlitz 地图风格改造
├── 路线 A：Godot 4 · 2D 等距 TileMapLayer + 分层高度模拟
│   ├── 优点：保留现有 2D 精灵 / UI / Python 后端，改动集中在地图层
│   ├── 缺点：高度靠"分层 + z_index"模拟，复杂场景遮挡需手工调
│   └── 结论：★★★ 推荐首选
├── 路线 B：Godot 4 · 3D GridMap + 正交相机（真 3D）
│   ├── 优点：高度天然存在、遮挡由引擎深度缓冲解决、体积光/阴影免费
│   ├── 缺点：单位精灵 / UI / 特效 / 寻路全部要迁到 3D，工作量 = 另一个项目
│   └── 结论：★ 视觉效果天花板，但现阶段不建议
└── 路线 C：2D 自写 Shader 伪 3D 高度
    ├── 优点：理论上最灵活
    ├── 缺点：鼠标拾取 / 遮挡 / 特效全要自己写，Godot 生态无参考
    └── 结论：✗ 不推荐（自己造轮子）
```

**决策要点**：路线 A 和 B 的差别，本质是**"美术资产以 2D 贴图交付"还是"以 3D 模型交付"**。BattleBlitz 目前有 15 个兵种立绘 + 6 张主角像 + 大量 2D UI，全是 2D 资产。选 B 意味着这些全部重做。

## 5. 路线 A 深入：Godot 4 2D 等距 + 分层高度

### 5.1 Godot 原生支持等距（已确认）

Godot 4 的 `TileSet` 有 `tile_shape` 属性，可选 `Isometric`，配合 `tile_layout = Diamond Down` 和 **2:1 比例**的 `tile_size`（例如 64×32、32×16、96×48）。设置完以后：

- 格子在屏幕上自动呈菱形排布；
- `TileMapLayer.local_to_map()` / `map_to_local()` 直接做屏幕↔格子换算，**不用手写偏移**；
- 引擎自带 `y_sort_enabled` 做深度排序。

社区经验总结（`0xheycat/isometric-game-skills` 的 `godot4-isometric-tilemap` 技能文档，明确写了"哪些做法是反模式"）：

| 反模式 | 为什么错 | 正确做法 |
|--------|--------|---------|
| 手写屏幕↔格子换算 | Y-sort 和缩放下会错位 | 用引擎内置 `local_to_map` / `map_to_local` |
| 手动微调 sprite 偏移 | 一缩放就崩 | 把 `y_sort_origin` 设到角色**脚底** |
| Y-sort 没开 / origin 留默认 (0,0) | 角色穿模、树冠盖头 | 父节点 + 瓦片层都开 y-sort |
| 不同层用不同 tile 尺寸 / 锚点 | 单位与地块对不齐 | 全项目统一一套 tile 尺寸与锚点约定 |

像素画另有 **2:1 像素法则**：菱形宽度 = 2 × 高度，斜线才是真正的 45°（这是像素等距的标准做法，比传统 30° 更好画）。

### 5.2 高度差的标准实现：分层 + z_index

Godot 2D 没有 per-cell elevation，**社区已验证的标准解法是"按高度分层"**：

```
场景树（等距版）
├── World (Node2D, y_sort_enabled = true)      ← 父节点开 y-sort，所有子节点按 Y 排序
│   ├── HeightLayer_0 (TileMapLayer, z_index = 0)   ← 高度 0 的地块
│   ├── HeightLayer_1 (TileMapLayer, z_index = 1)   ← 高度 1 的地块
│   ├── HeightLayer_2 (TileMapLayer, z_index = 2)   ← 高度 2 的地块
│   ├── ...
│   ├── DecorLayer  (TileMapLayer)              ← 树冠 / 屋顶等压在头顶的装饰
│   └── Units       (Node2D, y_sort_enabled)    ← 单位，y_sort_origin = 脚底
```

**规则**：
1. 每个高度一层 `TileMapLayer`，**层的 z_index = 高度值**。
2. 玩家在高度 0 时，跨到高度 1 的地块上，就把玩家节点的 z_index 改成 1——于是玩家正确地画在"高度 1 地块之上、但仍在高度 0 地块之下"。
3. 每块高地的**侧面**（立方体的两个可见面）作为独立贴图画在对应高度的层里，这样落差自然显现。
4. 每格高度记在 TileSet 的 **custom data layer**（整数类型），寻路时读 `tile_data.get_custom_data("elevation")`。

这套做法在 Godot 论坛有完整的实战讨论（"Godot Tilemap depth sort"），并被多人验证可行；itch.io 上也有配套的完整教程 demo（见 §8）。

### 5.3 路线 A 的真实难点

**Y-sort 单独用是不够的。** 论坛原话：地块因为有高度被视觉上移到了上方（负 Y 偏移），但它在网格逻辑上仍然"在角色前面"，此时 Y-sort 会判错。解法就是上面的"分层 z_index"——把高度差从"排序问题"转成"图层问题"。

**代价**：如果地图有 4 个高度差，就要 4 层 TileMapLayer，且每层要画各自的顶面 + 侧面。地图越大，层数×贴图量的乘积越可怕。

## 6. 路线 B 深入：Godot 4 3D GridMap + 正交相机

Godot 4 内置 `GridMap` 节点，天然支持**逐格 Y 高度**（`set_cell_item(Vector3i(x, y, z), ...)`），配一个 `Camera3D`（projection = ORTHOGONAL，旋转 45°）就能得到和 2D 等距几乎一样的画面，但：

- 高度是真几何，侧面由模型生成，**不需要画侧体贴图**；
- 遮挡由深度缓冲天然解决，**不需要分层 z_index**；
- 光照、阴影、雾全部免费。

配套的成熟开源生态：

| 项目 | 说明 | 适合度 |
|------|------|:---:|
| **Terrain3D** | C++ GDExtension，几何 clipmap 地形，最高 16k×16k、10 级 LOD、32 套纹理，支持高度图导入 | ⭐⭐⭐ 真 3D 地形首选 |
| **godot_heightmap_plugin**（Zylann） | GDScript 实现的高度图地形，四叉树 LOD、异步碰撞、多纹理混合，源码全可读可改 | ⭐⭐ 适合中小规模 |
| **GridMap + MeshLibrary** | 引擎内置，零依赖，适合「方块化」的山脉 | ⭐⭐⭐ 战棋方块地形最贴切 |

**但对 BattleBlitz 的判断**：这条路要动的东西包括——所有单位 Sprite2D → Sprite3D/AnimatedSprite3D、地图预览渲染器、相机控制（board_camera.gd）、鼠标拾取（2D raycast → 3D）、Y-sort → 深度测试、以及全部 2D UI 叠加层的处理。**这不是"改地图风格"，这是"重写客户端渲染层"**。建议留作 Phase 3 的备选，先不投。

---

## 7. 路线 C：2D Shader 伪高度（不推荐）

理论上可以用 shader 做顶点位移 + 侧面生成，灵活度最高。但：

- 鼠标拾取要自己写逆变换；
- 遮挡排序仍要手工解决（shader 改不了绘制顺序）；
- Godot 生态**零参考实现**，等于自己造轮子；
- 与项目"不写臃肿代码、主动避免过度设计"的取向相悖。

**明确排除。**

## 9. 数据模型改造方案

### 9.1 当前状态

BattleBlitz 的地图是**纯字符网格**，没有任何高度概念：

```json
{
  "size": 15,
  "biome": "grass",
  "layout": ["C........C", "..........", ...],
  "initial_units": [...]
}
```

- 字符表定义在 `game/app/game_logic.py` 的 `_layout_to_tiles()`；
- 落地为 `game/app/models.py` 的 `Tile` 表，字段：`x / y / terrain / subtype / owner_id / occupied_unit_id`；
- Godot 侧由 `godot-client/scripts/core/map_loader.gd` 的 `apply_to_board()` 读 JSON 后写进 TileMapLayer。

### 9.2 建议：新增 elevation 网格（与 layout 同构）

**保持向后兼容**——不写 `elevation` 的老地图一律当作全 0，零迁移成本。

```json
{
  "size": 15,
  "biome": "grass",
  "layout": ["C........C", "..........", "..."],
  "elevation": [
    "000000000000000",
    "001222222110000",
    "001233333210000",
    "000011111000000"
  ],
  "initial_units": [...]
}
```

**规则**：

| 项 | 约定 |
|---|---|
| 字符 | `0`-`9` 表示高度层数，**0 为基准地面** |
| 维度 | 必须与 `layout` 完全一致（行数 = height，每行长度 = width） |
| 缺省 | 整个 `elevation` 字段缺失 → 全 0（老地图零改动） |
| 语义 | 数值是**相对高度层**，不是绝对海拔；相邻格高度差 > 1 时即为悬崖 |
| 校验 | 与 `layout` 同样在加载期 raise `ValueError`，不静默截断 |

### 9.3 后端与前端的双端影响

| 层 | 需要改什么 |
|---|---|
| **Python 后端** | `Tile` 表加 `elevation: int` 列（需 Alembic 迁移）；`_layout_to_tiles()` 解析 elevation；地图生成器 `game_logic.py` 的 `generate_map()` 产出带高度的地图；`movement.py` 的寻路要读高度差 |
| **Godot 客户端** | `map_loader.gd` 按 elevation 分发到不同高度层；`map_metrics.gd` 的坐标换算从正交改成等距 |
| **地图生成工具** | `tools/gen_map_presets.py` / `gen_map_json.py` 生成的地图需要配套 elevation；`tools/visualize_map.py`、`tools/render_map_preview.py` 的预览渲染器要同步支持等距 |

### 9.4 玩法层：高度差不只是好看

一旦有了 elevation，下面这些规则才有意义（这是老大这个需求真正的玩法红利）：

- **移动代价**：上坡 / 下坡是否额外消耗移动力（FFT 思路）
- **跳跃限制**：落差 ≥ 2 格不可直接攀爬（对应 FFT 的 Jump 属性）
- **视线（LOS）**：高地视野更远；高地可越过低地射击
- **射程**：远程攻击需要考虑高度差（FFT 的射程计算包含高度）
- **伤害**：高地单位获得防御加成（FFT 的地形加成机制）

> ⚠️ 这些**都还没在 BattleBlitz 里实现**。如果只是"画得好看"而不落规则，高度差就只是一层皮，后续会被策划反复要求补规则。建议在设计文档里明确：高度差是**先做视觉、再补规则**，还是**视觉与规则同批上线**。

## 10. 对现有代码的改动点清单

以下是基于实际代码读取得到的定位，供排期用。

### 10.1 坐标系统 —— 影响最大

**`godot-client/scripts/core/map_metrics.gd`**（全文 59 行）：

```
L5   const TILE_SIZE: Vector2i = Vector2i(48, 48)     ← 改成等距 2:1，如 96×48
L6   const HALF_TILE: Vector2 = Vector2(24.0, 24.0)
L49  func cell_origin(tile)     →  return Vector2(tile.x * TILE_SIZE.x, tile.y * TILE_SIZE.y)
L53  func cell_to_local(tile)   →  origin + HALF_TILE
L57  func local_to_cell(pos)    →  floori(pos.x / TILE_SIZE.x), floori(pos.y / TILE_SIZE.y)
```

这三行是**正交网格的线性换算**，等距下完全不成立。必须换成菱形投影：

```
等距 2:1 的标准换算（tile 宽 W、高 H，即 W = 2H）：
    screen_x = (tile.x - tile.y) * (W / 2)
    screen_y = (tile.x + tile.y) * (H / 2) - elevation * LEVEL_HEIGHT
    反解：  tile.x = (screen_x / (W/2) + screen_y / (H/2)) / 2
            tile.y = (screen_y / (H/2) - screen_x / (W/2)) / 2
```

> 更稳的做法：**直接用 TileMapLayer 自带的 `local_to_map()` / `map_to_local()`**，让引擎算，避开手写公式出错。但要注意 `map_metrics.gd` 提供的 `cell_to_local` 被 `board.gd` 多处调用（单位移动 tween、高亮、移动范围预览），要么改成薄封装转发给引擎 API，要么保留手写公式并写往返测试。

### 10.2 瓦片与图层

**`godot-client/scripts/core/tile_set_builder.gd`**（20.9 KB）：

- `L66  ts.tile_size = TILE_SIZE` → 需改为等距 2:1，且 TileSet 的 `tile_shape` 要设为 Isometric、`tile_layout` 设为 Diamond Down；
- 现有 FE8 母版图集是 **512×512、32×32 个 16×16 子块的正视角像素图**（见 L6-8 注释），**这套美术无法直接转等距**，必须换图集；
- `L118 atlas_coord_for(terrain, biome, x, y)` 的变体索引逻辑要按新图集重写。

**`godot-client/scripts/core/map_loader.gd`**（5.2 KB）：

- `L28-30` 三个 layer 的 `clear()` → 改为按高度层级管理；
- `L93 _apply_layer_cell()` → 写入时需要按该格 elevation 选择目标层。

### 10.3 棋盘与相机

**`godot-client/scripts/board/board.gd`**（40.3 KB）：

- `L383` `existing.position = metrics.cell_to_local(Vector2i(expanded_path[0]))` —— 单位初始位置；
- `L392` `tween_property(existing, "position", metrics.cell_to_local(Vector2i(cell)), step_sec)` —— 单位走格动画；
- `L762 viewport_to_tile(pos)` —— 屏幕坐标反查格子；
- `L164 pick_unit_at_screen(global_pos)` —— 点选单位；
- `L483-512` 相机平移/缩放边界 —— 等距下地图的包围盒是**菱形**，现有的 `Rect2` 边界算法要重写。

**`godot-client/scripts/board/board_camera.gd`**（11.6 KB）—— 边界钳制逻辑同上。

**`godot-client/scripts/board/highlights.gd`**（10.9 KB）—— 移动范围高亮、等距下要画菱形而非矩形。

**`godot-client/scripts/core/map_theme.gd`**（2.4 KB）—— 地形→图层的路由表，改等距后结构不变，但需要新增"高度"维度。

### 10.4 现有调研文档的冲突点

**`docs/路线/参考调研/2026-07-13-godot-地图渲染梯度方案.md`** 的 Tier B 定义为「标准 TileMap + autotile（FE8 美术）」，并把 Tier S 定义为「商业级 2.5D」—— 当时的路线图里，"等距 + 高度"并不在梯度表内。**本次改造实际上是把 Tier S 的方向具体化成了"等距 + 高度差"**，原梯度表需要修订。

**`docs/路线/参考调研/2026-07-14-godot-2d-map-patterns.md`** 的 6 个 Pattern（Gameboard autoload / GameboardProperties / Camera autoload 等）中，Pattern 2（`cell_to_pixel` / `pixel_to_cell`）和 Pattern 4（相机动态 limit）**在等距下必须重写**，其余（GameboardProperties 资源、GameboardLayer 子类、custom data layer 通行性、Path2D 移动）**仍然适用**。

## 11. 美术资产策略：3 条路，代价差一个数量级

这是整个改造的**成本主战场**，必须老大拍板。

| 策略 | 做法 | 成本 | 风险 |
|------|------|:---:|------|
| **① 全 AI 生成等距瓦片** | 用现有 `tools/gen_terrain_tiles.py`（PIL 程序化绘制，48×48）改写成等距 2:1（96×48 顶面 + 侧面），批量产出 | 低（人天） | 像素风一致性差，需要人工挑修 |
| **② 采购/下载等距资产包再改造** | 用 cozyconsoleco / depth-strider 的包做底，把水墨/古风配色刷上去 | 中 | 授权限制（不可转售）、风格与项目现有水墨风有距离 |
| **③ 全手工绘制等距立方体贴图** | 顶面（俯视纹理）+ 左侧面 + 右侧面，每种地形 × 每个高度差 | **高（周级）** | 高度差组合爆炸（4 地形 × 5 高度 × 3 面 = 60 张起） |

**建议路径**：①打底 + ②补关键资产 + ③只精修主角周边。

> 参考：`tools/gen_terrain_tiles.py` 已经是一个 40 KB 的程序化像素瓦片生成器（GBA 风格调色板：草地 3 阶、森林 3 阶、山地 4 阶、雪顶等），**改造它去产出等距立方体是成本最低的路径**，比从零画起划算得多。
>
> 但要注意：程序化生成只能产出"规整的立方体"，做不出自然山脊的破碎轮廓。山脉的地形轮廓本身（哪些格是山、怎么连成脉）由 `tools/gen_map_presets.py` 的地图生成器决定，**这块要单独调**。

## 12. 分阶段落地计划

```
Phase 0 · 技术验证（2-3 天）★ 先做这个，别急着改主工程
│   ├── 在 godot-client 下开一个隔离 demo 场景
│   ├── 搭 4 层 TileMapLayer 等距网格，导入 depth-strider / cozyconsoleco 资产
│   ├── 验证：高度分层 z_index、Y-sort 遮挡、鼠标拾取、单位走格
│   └── 产出：一页「可行 / 不可行」结论 + 性能基线
│
Phase 1 · 数据模型（3-5 天）
│   ├── 后端：Tile 表加 elevation 列 + Alembic 迁移
│   ├── 后端：_layout_to_tiles() 解析 elevation + 校验
│   ├── 前端：map_loader.gd / map_metrics.gd 支持等距 + 高度
│   └── 产出：现有 10+ 张地图全部自动补全 elevation=0，不破坏任何旧逻辑
│
Phase 2 · 渲染层迁移（5-8 天）
│   ├── TileSetBuilder 切等距 TileShape + 换图集
│   ├── board.gd / board_camera.gd / highlights.gd 的坐标与边界算法重写
│   ├── 单位层接入 y_sort_origin（脚底锚点）
│   └── 产出：一张等距地图能完整跑通「选单位 → 走格 → 攻击 → 结算」
│
Phase 3 · 地形资产（10-15 天，可与 Phase 2 并行）
│   ├── 改造 gen_terrain_tiles.py → 等距立方体生成器
│   ├── 每种地形出：顶面 + 左侧 + 右侧
│   ├── 高度差组合：阶梯 / 坡道（专门资产）
│   └── 产出：plain / forest / mountain / river / castle / village / barracks 全套等距资产
│
Phase 4 · 地图内容与玩法（并行推进）
│   ├── 地图生成器产出带山脉高度差的地图
│   ├── 高度相关玩法规则（跳跃 / 移动代价 / 视线 / 射程）设计与实现
│   └── 产出：至少 3 张有山有谷的新地图
│
Phase 5 · 回退方案
    └── 若 Phase 0 结论不通过 → 保留现有正交渲染，走 §11 的"仅换美术"轻量路线
```

**关键节点**：Phase 0 是**唯一必须先做的**。等距 + 高度的遮挡排序（§5.3）有已知坑，不在隔离 demo 里验证就动主工程，返工成本会翻倍。
