## 2. 为什么回退

FE-like 探路分支证明了一些方向有价值:前五章内容数据、数值校准测试、截图 harness、战斗内事件插入尝试。但它没有形成可靠的客户端架构:

- Godot 端大量流程继续集中在 `godot-client/scripts/main.gd`,没有拆出主线流程控制器、剧情 runner、战斗事件 director、行动菜单 controller。
- 没有清晰区分章节循环、战前准备循环、战斗回合循环、单位行动循环、剧情插入循环。
- 截图验收存在假阳性:部分截图只验证节点可见和非空,没有验证关键文本/数值。
- 部分事件链路只做到上下文透传,没有完成可模板化的战斗内演出系统。

因此 FE-like 分支定位调整为**参考原型**。后续若继续做 FE-like 风味,应从当前 `master` 重新建立结构化模块,只按需 cherry-pick 小型、可验证的修复或内容资产。

## 6. 建议的下一阶段路线

下一阶段不建议继续在 `main.gd` 里堆 FE-like 逻辑。建议从当前 `master` 新建一个普通命名分支,例如:

```powershell
git switch master
git switch -c fe-like-runtime-architecture
```

第一批任务应聚焦结构,不要先复刻大量剧情:

1. 修复当前 Godot smoke 的 sprite canvas 失败,保持基线自动化全绿。
2. 新建 Godot FE-like 流程模块,最少包含:
   - `FeLikeChapterFlow.gd`:章节标题、战前对话、准备、进入战斗、胜利后推进。
   - `FeLikeSceneRunner.gd`:dialogue/narration/choice/wait/battle_ref 的统一播放。
   - `FeLikeBattleEventDirector.gd`:回合开始、增援、NPC 入场、战斗对话、招募、村庄/宝箱/门事件。
   - `FeLikeActionMenu.gd`:单位行动菜单和攻击预测 UI 的独立控制。
3. 后端扩展事件 schema,区分 `chapter_scene`, `battle_turn_event`, `unit_action_event`, `recruitment_event`, `tile_event`。
4. 只做“序章/第一章纵切”:战前对话 -> 准备 -> 入战斗 -> 回合事件 -> 胜利后对话 -> 自动存档。
5. 纵切验收必须包含后端测试、Godot smoke、截图断言、至少一条真实后端到 Godot 的端到端流程。

## 7. 不再推荐的路线

- 不建议直接恢复 `archive/2026-07-21/fe_like` 继续开发。
