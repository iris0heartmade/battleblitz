# 职业与英雄地形行动修正规划

日期：2026-07-14

## 目标

在现有“地形决定移动消耗与通行性”的基础上，支持：

- 不同职业对不同地形具有不同的进入消耗或通行限制。
- 英雄在所属职业规则之上，拥有额外的地形行动修正。
- 人类玩家、规则 AI、LLM AI、前端可达范围和实际服务器校验完全一致。

例如：骑士穿越道路更快、弓手进入森林消耗更低、法师不能进入山地；某英雄可额外降低河流消耗或允许进入原本受限的地形。

## 现状

当前基础地形成本集中在 `game/app/config.py` 的
`TERRAIN_MOVE_COST`，以 `x2` 整数表示：平地 `2`、森林 `4`、
山地/河流 `6`、道路/桥梁 `1`。`gate` 与 `castle_wall` 对所有单位
不可通行。

当前不存在职业或英雄的地形移动规则：

- 职业只定义基础 `mov` 与 `mp`，见 `game/app/classes/units/base.py`。
- 英雄只定义基础数值覆盖，见 `game/app/classes/heroes/base.py`；战斗单位已有 `hero_id`，因此运行时可以识别英雄，无需复制规则到数据库。
- 人类移动、规则 AI、LLM AI 合法动作、前端可达范围各自调用/镜像成本表。若直接在某一处加条件，会出现“前端可点但服务端 400”或 AI 违规移动。

## 推荐规则模型

新增不可变的“移动档案”，按以下顺序合并：

`全局地形默认值 -> 职业修正 -> 英雄修正`

同一地形上英雄规则优先于职业规则。建议每条规则支持：

| 字段 | 含义 |
| --- | --- |
| `cost_override_x2` | 将进入该地形的成本直接改为指定 x2 值 |
| `cost_delta_x2` | 在当前成本上加减；结果不得小于 1 |
| `can_end_on` | 显式允许或禁止在该格结束移动 |
| `can_traverse` | 可将该格作为路径中的越过格，但不代表可在此停留 |

### 声明式配置格式

该能力必须是格式化、数据驱动的修改，而不是在寻路代码中写“如果是
天马”或“如果是山脉”的特殊分支。职业和英雄统一使用同一个字段格式；
引擎只解释字段，不认识具体职业名称。

建议职业/英雄定义使用如下 Python 数据结构（后续也可无损迁移为 JSON）：

```python
terrain_movement = {
    "forest": {"cost_delta_x2": -2},
    "mountain": {"can_traverse": True, "can_end_on": False, "cost_override_x2": 2},
    "river": {"can_traverse": True, "can_end_on": True, "cost_override_x2": 2},
    "castle_wall": {"can_traverse": True, "can_end_on": False, "cost_override_x2": 2},
}
```

天马职业只需声明上面的 `terrain_movement`；某个英雄若能在森林落脚或
免费飞越河流，则只在其英雄定义中声明同格式条目。合并规则固定为：

1. 读取全局地形默认配置。
2. 应用职业条目。
3. 应用英雄同名条目覆盖；未填写的字段继承职业结果。
4. 校验成本、地形名和 `can_end_on -> can_traverse` 等不变量。

这样新增飞行、两栖、山地、潜行等职业只改内容定义和测试矩阵，不需要
为每个职业修改 `pathfind`、AI 或前端条件判断。

全局硬阻挡 `gate` 与 `castle_wall` 保持不可作为落点；只有明确声明
飞行穿越能力的职业或英雄可越过它们。敌方 HQ 仍可进入，并继续通过
两回合占领改变所有权。

### 飞行职业规则

天马等飞行职业需要区分“越过”与“落点”：

- 可跨越山脉、雪峰、河流、城墙及建筑阻挡格，不因这些格子中断路径。
- 默认不能在 `castle_wall`、`gate` 等墙体/闸门格结束移动，也不能对其执行占领、招募或驻守。
- 可落点的建筑（例如城堡、村庄、兵营）仍由普通 `can_end_on` 与占领规则决定；飞行不自动绕过敌方单位占格。
- 飞行的跨越成本应由职业规则明确声明，例如“所有跨越地形按 1 MP”或“山脉/河流按 1 MP”，不隐含免费移动。

因此移动档案的接口应拆分为：

- `can_traverse_terrain(profile, terrain, ...)`：路径扩展时判断。
- `can_end_on_terrain(profile, terrain, ...)`：目的地/停留时判断。

寻路需要允许中间节点使用 `can_traverse_terrain`，但只有
`can_end_on_terrain` 为真的节点才进入可选终点集合。这样天马可以从
城墙一侧飞到另一侧，却不能把单位放在城墙格上。

### 有效地形键

实现前必须统一“有效地形键”：`movement_key = tile.subtype or tile.terrain`。
城堡墙、门、王座等目前以 `Tile.subtype` 保存，`Tile.terrain` 仍为
`castle`。若寻路只读取 `terrain`，会把城墙误判为普通城堡，导致飞行
规则、普通阻挡规则和前端预览全部失效。

`app/movement.py` 应提供 `movement_key(tile)`；人类移动、规则 AI、LLM
AI、前端状态契约均使用该键。地形占位是独立硬规则：飞行能力不允许穿过
已被单位占据的格子。

建议新增 `app/movement.py` 作为唯一规则入口：

- `resolve_movement_profile(unit)`：根据 `unit.unit_type` 与 `unit.hero_id` 合并职业、英雄规则。
- `terrain_cost_x2(profile, terrain)`：返回实际进入成本。
- `can_end_on_terrain(profile, terrain, owner_id, viewer_owner_id)`：返回单位级落点判断。

`utils.py` 不应直接导入 ORM 或英雄注册表。它接收已解析的移动档案/成本回调，保持寻路工具可测试、无数据库依赖。

## 实施范围

| 层级 | 文件/模块 | 改动 |
| --- | --- | --- |
| 规则数据 | `app/classes/units/base.py` 与各职业文件 | 为职业声明地形修正，并编译进 `UnitClassProfile` |
| 英雄数据 | `app/classes/heroes/base.py` 与英雄定义文件 | 为英雄声明覆盖/加成规则，并编译进 `HeroProfile` |
| 规则解析 | 新增 `app/movement.py` | 合并优先级、成本和通行判定的唯一真源 |
| 寻路 | `app/utils.py` | `bfs_reachable`、`pathfind` 接收有效移动档案/成本回调，并区分可跨越节点与可落点终点；改为一致的 Dijkstra 处理非等权成本 |
| 人类动作 | `app/routes/actions.py` | 服务端寻路、成本复算、MP 扣除全部使用有效档案 |
| 规则 AI | `app/game_logic.py` | 可达格、路径选择、实际移动与成本扣除使用有效档案 |
| LLM AI | `app/agent/legal_actions.py` | 合法移动枚举使用同一有效档案 |
| 状态契约 | `app/schemas.py`、状态路由 | 向客户端下发单位的已解析有效移动档案，并让 Tile 提供/派生 `movement_key` |
| 前端 | `app/web/app.js` | 删除硬编码成本作为主逻辑，改用服务端下发档案计算高亮、路径预览和预计成本 |
| 测试 | `test_utils.py`、动作/AI/主线英雄测试 | 覆盖职业、英雄优先级、通行禁止、扣费、AI 与前端契约 |

预计核心改动为 10-14 个生产文件、5-7 个测试文件。职业/英雄具体平衡数据不计入框架开发量。

## MP 精度决策

当前成本采用 x2 表示，但 `Unit.mp` 是整数，移动扣费使用向下取整；因此现有道路/桥梁的 `0.5 MP` 会产生免费余数。地形修正若引入更多半步成本，会放大该平衡偏差。

有两种可选范围：

### 方案 A：整点 MP MVP（推荐第一期）

- 新职业/英雄修正的最终成本必须为偶数 x2，即整点 MP。
- 保留既有道路/桥梁的半步兼容行为，不在本需求中改变存档与数据库；因此含道路/桥梁的路径仍可能因现有向下取整而获得免费 `0.5 MP` 余数。
- 不新增表字段；适合先验证职业差异和英雄天赋。
- 预计 2-3 个开发日，外加 1 个测试/平衡日。

### 方案 B：精确半步 MP

- 新增持久化的 `mp_x2`（或等价移动余数）并迁移 `Unit`、状态 API、回合重置、存档/中断恢复、AI 与前端显示。
- 所有成本可精确使用 0.5 MP，适合道路、河流和职业天赋做细颗粒平衡。
- 需要处理旧存档默认值及展示层换算。
- 预计 4-6 个开发日，外加 2-3 个回归与存档兼容日。

建议先选方案 A，但必须接受并在平衡测试中记录既有半步免费余数。若飞行、道路或英雄天赋需要严格的 `0.5 MP` 平衡，应直接选择方案 B。规则模型须从第一天起使用 x2 单位，未来升级方案 B 时仅替换 MP 账本，不重写职业/英雄配置。

## 分阶段计划

1. 确认首批职业/英雄与地形矩阵，以及选择方案 A 或 B。
2. 实现 `movement_key`、格式校验与移动档案；明确跨越节点和落点集合。
3. 实现服务端 Dijkstra 寻路与人类移动成本统一。
4. 接入规则 AI、LLM AI 和状态 API；统一使用剩余 `unit.mp` 而非基础 `unit.mov` 作为本回合预算。
5. 接入前端高亮、路径预览、预计消耗；在单位信息中展示当前地形行动特性。
6. 增加矩阵、扣费、AI、主线英雄及存档回归测试。
7. 使用 2-3 张含道路、森林、山地、河流、城堡的地图进行人工平衡测试。

## 风险与验收

- 风险：前端与服务器已有独立成本实现，必须以服务器下发数据为准。
- 风险：城堡子类型存在于 `Tile.subtype`；未统一有效地形键会使墙/门规则失效。
- 风险：规则 AI 目前有少量路径调用使用 `unit.mov` 而非剩余 `unit.mp`；接入时应一起修正，否则 AI 会获得额外行动范围。
- 风险：地图生成仍按全局通行性保证连通；首批配置不能让所有常规职业失去基本路线。

验收标准：同一单位、同一地图、同一 MP 下，前端高亮、`POST /move`、规则 AI、LLM AI 合法动作给出的可达格与实际消耗一致；英雄覆盖只影响带对应 `hero_id` 的单位；旧存档与现有地图仍能正常加载。

飞行职业额外验收：天马能越过山脉/河流/城墙到达另一侧合法落点；不可把城墙或闸门显示为可选落点；无法越过被其他单位占据的格子；AI 与前端预览路径和服务端结果一致。
