# Godot UI 问题修复设计

日期：2026-07-24
范围：5 张用户标注截图对应的 Godot 客户端问题

## 目标

在不重写现有 UI 架构、不改变服务端规则的前提下，修复大厅座位状态、主线页面控件、存档页面布局、启动过渡流程和战斗立绘显示区域。所有修改必须保留现有 NetworkClient 回调契约与 server-authoritative 数据来源。

## 设计

### 1. 大厅 AI 替补

以座位状态为单一渲染入口。未占用且未启用 AI 替补时显示“等待玩家入座”；启用 AI 替补时先显示本地占位“电脑-N（入座中…）”，服务端刷新后使用 `is_ai` 玩家名称或稳定的 AI 名称。AI 替补开关、移除和轮询刷新都通过同一个座位渲染函数更新，避免本地空字符串覆盖 AI 状态。

### 2. 主线章节页面

`_set_mainline_page()` 负责所有页面控件的可见性：章节列表页隐藏全部战前整备控件，准备页显示整备控件。修复 `MLPrepCompleteBtn` 未纳入页面切换的问题，并保留按钮信号连接。对重复固定位置的底部控件进行明确的互斥布局/可见性处理，避免控件覆盖导致点击事件被遮挡。

### 3. 存档管理页面

沿用现有 `saves_controller.gd` 的动态行渲染，不用更多固定坐标补丁。将标题、槽位列表、自动存档、中断存档和底部操作按钮分成垂直区域，保证动态槽位行不会与分区标题重叠。删除中断存档操作仍使用现有 API，不改变存档语义。

### 4. 大厅启动流程

追踪大厅开始按钮 → start API → start response → connecting/game view 的完整链路。移除仅用于展示“配置完成，正在开启游戏…”的冗余停留状态；成功启动后直接切换到游戏视图并建立连接，失败时仍在大厅显示可理解的错误。不得跳过必要的 state snapshot 初始化。

### 5. 战斗立绘区域

不缩放原始立绘资源。定位截图红框对应的 HUD/角色面板节点，调整其容器尺寸、锚点、裁剪与对齐方式，使立绘在目标框内按原始像素绘制；必要时使用滚动/裁剪容器承载超出区域的图片，而不是改变纹理尺寸。只影响该立绘展示组件，不改变棋盘摄像机或单位贴图。

## 测试与验证

- 扩展 Godot 客户端合约测试，覆盖页面控件互斥可见性和 AI 替补文案逻辑。
- 运行现有后端/Godot contract 测试，确认 NetworkClient 回调签名没有回归。
- 启动 Godot 客户端进行大厅、主线、存档和战斗视图的真实流程验证，并重新截图对比 5 个问题。
- 若运行环境无法启动 Godot，明确记录阻塞原因，并至少完成静态合约测试与脚本解析检查。

## 非目标

- 不重写大厅或主线 UI 架构。
- 不修改后端座位、AI、存档和主线 API 语义。
- 不更换立绘资源、不对立绘做图像缩放。
- 不顺手修复未在这 5 张截图中体现的其他视觉问题。
